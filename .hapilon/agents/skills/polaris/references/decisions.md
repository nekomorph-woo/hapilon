# 决策记录

实现与设计中遇到前期规则没有覆盖的决定时，登记在项目级一张表 `.hapilon/polaris/decisions.md`，跨工作共用。它是受托决定的留痕处，也是用户异步回来时的待办入口：人不需要翻对话，看这张表就知道哪些决定在等拍板。

## 登记时机

遇到产品或技术决定，先查已有授权与已在案决定：

- 授权覆盖：按授权执行，状态记「受托已定」，注明所依据的授权。
- 授权不覆盖：登记为「待确认」，按当时条件选最推荐的选项继续实现，不阻塞等待。改变已确认业务预期、范围或安全边界的决定除外，这类仍暂停并说明影响。
- 同一问题已有在案决定时复用该行，不重复登记。

## 表格式

| ID | 决定（what） | 背景（why） | 备选方案 | 当时选择与理由 | 状态 | 影响面 |
|---|---|---|---|---|---|---|

- ID 项目内唯一，如 `DEC-014`。
- 状态取值：待确认、受托已定、已拍板、已否决。
- 影响面列出受该决定约束、或拍板后需要改动的对象：规则登记条目、Case ID、实现位置、文档。拍板前它回答「改这里会牵动什么」，拍板后它是回写清单。
- what/why/备选/理由在登记时一次写全；拍板结果与依据由用户给出，主持者代记。

## 拍板与回写

用户拍板后：

1. 更新状态与结果。已否决的保留原行不删——它记录着当时为什么那样选。
2. 按影响面逐项回写：受影响的规则登记、Case Expected、代码、文档跟随变更。
3. 重跑受影响 Case；旧结果不延续到新决定之后。
4. 受托已定的决定同样可被用户推翻，推翻走同一条回写路径。

## 边界

- 决策记录不替代范围审核：改变本轮范围仍回切片与业务设计确认，这里只留痕。
- 实现自由度内的纯技术风格选择不是决定，不登记。
- state.md 的「已确认决定」引用这里的 ID 与摘要，不抄写全文。
