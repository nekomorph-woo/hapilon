# 追问协议参考

## 核心原则

Interview the user relentlessly about every aspect of the question until shared understanding is reached.

Walk down each branch of the decision tree, resolving dependencies between decisions one-by-one.

## 为什么追问

用户提问模糊通常不是因为"不会表达"，而是：

- 自己还没想清楚要问什么
- 以为你知道上下文（其实你不知道）
- 问题本身嵌套了多个子问题

追问的目的不是刁难用户，而是帮用户**自己理清思路**——这个过程本身就是价值。

## 怎么追问

### 一次一个问题

```
❌ 错误（信息轰炸）：
"你要查哪个模块？是看代码逻辑还是看配置？关心性能还是正确性？需要我搜互联网吗？"

✅ 正确（逐一推进）：
"你要查哪个模块？我看项目里有 auth、api、config 三个核心模块。"
→ 用户回答后再问下一个
```

### 事实自己查，决策问用户

| 类型 | 处理方式 | 示例 |
|------|----------|------|
| 事实 | 自己去代码库查 | "这个函数签名是什么？" → grep 源码 |
| 决策 | 问用户 | "要用方案 A 还是方案 B？" → 列出优劣，推荐一个 |

### 附带推荐答案

每个问题都基于已知信息给出最佳猜测：

```
"这个错误看起来是 auth 模块的 token 过期导致的（代码库中 auth.ts:42 的超时设置是 5 分钟）。
你是不是在登录后等了超过 5 分钟才操作？如果是，解决方案是刷新 token。对吗？"
```

而不是：

```
"这是什么错误？"
```

### 沿决策树追问

```
用户: "这个接口好慢"
  ↓
Q1: "哪个接口？我看到项目里有 /api/users 和 /api/orders。"
  → A1: "/api/orders"
  ↓
Q2: "慢到什么程度？是刚变慢还是一直慢？"
  → A2: "刚变慢，以前 200ms 现在 5s"
  ↓
Q3: "最近有改过 /api/orders 相关代码吗？我看 git log 显示昨天有次提交改了 order 查询。"
  → ...继续深入直到定位根因
```

### 达成共识后再回答

不要边猜边答——追问阶段和回答阶段分离：

```
追问阶段：只问问题，不输出分析结论
  ↓ 用户确认理解一致
回答阶段：给出完整、结构化的答案
```

## 何时停止追问

满足以下条件时追问结束：

- 问题的所有模糊点已澄清
- 用户确认你对问题的理解正确
- 你有足够信息给出准确答案
