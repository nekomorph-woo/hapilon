# 动手前先设计

## 目标

把一份**已确认的需求**变成小而完整的设计，再进实现。

不是设计完整未来系统。是建立足够的共享理解：人能拍重要决策，AI 能带着清晰约束去实现。

不点名不写生产代码。

## 原则

- 为当前已确认的业务需求设计，不为想象中的未来需求设计。
- 主端到端流程先自洽，再钻局部细节。
- 在保住语义清晰、归属明确、关键约束成立的前提下，取最小设计。
- 不做投机抽象、预留扩展点、框架驱动的结构。
- 新需求真来了再让设计演化。
- AI 负责探选项、亮风险、挑假设；重要取舍与最终决策归人。

## 流程

### 1. 定框

澄清当前设计范围：

- 谁需要什么？
- 本轮迭代必须达成什么结果？
- 明确不做什么？
- 哪些假设或未知会实质影响设计？

问题空间与实现选型分开。

### 2. 走流

描述交付所需结果的最小有意义端到端流程。

从主路径起，先确保它抵达真正的完成点，再展开次要分支。只识别当前流程可信所需的失败与替代路径。

### 3. 建模

推导流程所需的概念与规则：

- 核心业务概念
- 重要关系
- 必须持久化的数据或状态
- 必须恒真的规则与不变量

不因「以后可能有用」建模。造新词前先查项目词汇表（`.hapilon/CONTEXT.md`）。

### 4. 划界

定重要职责归属：

- 谁拥有重要数据与行为？
- 副作用发生在哪？
- 哪些组件或外部系统必须交互？
- 哪些边界需要显式契约？

只定当前流程所需的边界。

### 5. 攻击

定稿前，让 AI 攻一遍这份设计：

- 哪个假设可能站不住？
- 漏了什么重要场景？
- 有没有职责不清或重复？
- 有没有多余的抽象？
- 能不能再简单一点而不丢正确性？
- 哪个决定翻代会很贵？
- 哪个用词与项目词汇表打架？

真实当下的风险与假想的未来担忧分开。

### 6. 排步

把通过的设计排成小的、纵向的、可验证的实现步骤。每步定义：

- 目标
- 预期行为
- 相关区域
- 重要约束
- 怎么验证

按能力排步，不按「写哪几个文件」排。

## 人审检查点

实现前汇总：

- 当前范围
- 端到端流程
- 核心模型
- 重要不变量
- 职责边界
- 关键设计决策
- 实现顺序
- 遗留风险与未知

有未决事项实质影响下一步时，停下等人拍板。否则标注：

`READY FOR IMPLEMENTATION`

## 归档

用户要把设计留档时，写进该任务的卷宗——HAPILON_HOME 下的
`plan-task/<YYYY-MM-DD-slug>/design.md`（`$HAPILON_HOME/plan-task/`；
devhapi：`~/.hapilon-dev/plan-task/`），与任务简报同放——`/tmp` 永远不是落点。

## 护栏

- 不设计完整未来系统。
- 不为可能的未来复用加抽象。
- 不自动展开每个边界情况。
- 不把实现结构当业务设计。
- 不替人静默做重要产品或架构决策。
- 需要人拍板时不机械走完全部阶段。

## 表达

平实、具体。

- 生僻项目术语与缩写首现即释。
- 具体流程与职责优先于抽象行话。
- 已知事实、假设、未知分开说。
- 不造词、不喊口号、不注水、不反复总结、不加没用的小标题。
- 从简单起，对当前决策有帮助再加细节。
