# 事后清理

刚落地的改动常带着赘肉：复述代码的注释、多余的防御、没人要的抽象。本技能是一道**人工闸门**：先只读审查出编号报告，用户逐条裁决后才执行修改——不存在一条命令自动跑完的路径。

## 流程

### 1. 定范围（check 阶段第一步）

- `/simplify`（无参数）→ 审 `HEAD` 这一次提交
- `/simplify --staged` → 审暂存区
- `/simplify <ref>` → 审某个 commit / branch / tag
- `/simplify A..B` → 审一段范围（git 双点语法）

用 `git diff` 取范围，**只读**，零写入。

### 2. 审查（产出编号报告）

对 diff 逐条审，每条发现编号、引用行、给置信度，格式：

```
N. [HIGH|MEDIUM|LOW] <文件:行> 问题一句话
   建议：<怎么改>
```

- **HIGH**＝机械安全（死代码、复述性注释）；**MEDIUM**＝要人判断上下文；**LOW**＝风格层面、大概率跳过。
- 报告末尾给统计：各档几条、预计净删行数。**报告完就停**，等用户裁决。

### 3. 人工闸门

用户回复批准的编号（如「apply 2,4」或「2 和 4 可以，其他不要」）。没批准就是没批准——不揣测、不打包搭售。

### 4. 执行（apply 阶段）

只对批准的编号动手：修改 → 跑 `npm run build` 与相关测试 → 逐条报告结果（改了什么、测试状态）。任何一条执行中发现前提不成立（比如删了才看见依赖），停下说明，不擅自扩大范围。

## 审查规则

**注释**——只三类注释有价值，其余都是删除候选：
1. 功能概括——非显而易见的块/函数上一行短句说明它做什么；
2. 设计决策（可选）——为什么这么写而不是那么写：取舍、约束、被否掉的替代方案；
3. 重大 bug 修复——bug 是什么、根因、为什么这个修复关得住它。

删除候选：复述代码的注释、叙述显而易见步骤的注释、教科书式科普注释。未被本 diff 触碰的行上的注释不在范围内。

同时标记「只指向外部文档或追踪器」的注释（章节号、ADR/设计文档 id、issue/PR/review id——如 "design §3.2"、"issue #42"）：锚点会随文档迁移失效，读者无法从中还原理由。建议把理由本身折进注释，或理由其实不有趣就删注释。

**防御式编程**——删除候选：包住不会 throw 的内部调用的 try-catch、对类型系统或前置代码已保证的内部数据的重复校验、静默回落值、空 catch、catch-and-continue。

**红线（绝不建议删）**：信任边界处的输入校验（用户输入、网络、文件、进程边界、外部 API）、防数据丢失的错误处理、安全措施、可访问性基线、用户明确要求保留的东西。

## 边界

- 只审给定范围的 diff，不扩展到全仓库。
- 报告用中文；代码、标识符保持原文。
- 与 ponytail-review 互补：那个审过度设计的存量库，本技能只管刚落地的改动。
