# 事后清理

刚落地的改动常带着赘肉：重复造的轮子、多余的复杂度、白费的功夫、修得不够深的补丁。本技能是一道**人工闸门**：先只读审查出编号报告，用户逐条裁决后才执行修改——不存在一条命令自动跑完的路径。

## 流程

### 1. 定范围

- `/simplify`（无参数）→ `HEAD` 这次提交 + 未提交的工作区改动（收尾常在提交前跑）
- `/simplify --staged` → 暂存区
- `/simplify <ref>` → 某个 commit / branch / tag；`/simplify A..B` → 一段范围

用 `git diff` 取统一 diff 作为唯一审查范围，**只读**，零写入。

### 2. 四视角审查（产出编号报告）

四个视角逐一过 diff（可派 subagent 并行；容量不足就在主会话逐个视角过，不合并视角）。每条发现：编号、`文件:行`、一句话问题、**具体成本**（重复了什么、浪费了什么、什么因此更难维护）、置信度。

**复用（Reuse）**——新代码重新实现了代码库已有的东西。grep 共享/工具模块与改动相邻的文件，点名应该改调的既有 helper。

**简化（Simplification）**——diff 新增的多余复杂度：冗余或可推导的状态、带微小变化的复制粘贴、深嵌套、留下的死代码。说出做同一件事的更简形式。

**效率（Efficiency）**——diff 引入的白费功夫：重复计算或重复 IO、本可并行却串行的独立操作、加进启动或热路径的阻塞工作；闭包/捕获环境构成的长持有对象（把整个外层作用域钉住整个对象生命周期——外层持有大值时就是泄漏）。说出更省的替代。

**深度（Altitude）**——每处改动是否修在正确的层：在共享基础设施上叠特例 = 修得不够深，优先泛化底层机制而不是加特例。另按 hapilon code_style 扫注释（三类有效注释之外皆是删除候选）与多余防御（重复校验、空 catch、静默回落——信任边界处的校验除外，那是红线）。

**红线（绝不建议删/改）**：信任边界处的输入校验、防数据丢失的错误处理、安全措施、可访问性基线、用户明确要求保留的东西。

置信度：**HIGH**＝机械安全（死代码、复述性注释、点名既有 helper）；**MEDIUM**＝要人判断上下文；**LOW**＝风格层面、大概率跳过。报告末尾给统计：各档几条、预计净删行数。**报告完就停**，等用户裁决。

### 3. 人工闸门

用户回复批准的编号（如「apply 2,4」）。没批准就是没批准——不揣测、不打包搭售。

### 4. 执行

只对批准的编号动手：修改 → 跑 `npm run build` 与相关测试 → 逐条报告结果。跳过项注明理由（会改变预期行为 / 修复远超本次 diff 范围 / 判为误报），不与之争论。执行中发现前提不成立（如删了才看见依赖），停下说明，不擅自扩大范围。

## 边界

- 只审给定范围的 diff，不扩展到全仓库；与 ponytail-review 互补（那个审过度工程，含新写的；本技能只管刚落地 diff 的可删可简项）。
- 报告用中文；代码、标识符保持原文。
