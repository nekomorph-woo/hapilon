# 写好一个技能

## 目标

产出一份能被正确路由、读一次就能照做的 SKILL.md。

好技能的判据：只在需要的情境被加载，加载后行为可观察地变化，不与每轮在场的系统提示重复。不满足就不该存在。

## 先判该不该造

按顺序过替代品，有命中就不写技能：

1. 每轮都该在场的纪律 → 系统提示或规则文件，不进按需加载的技能。
2. 同一句话写了第二遍 → 能编进结构就编进结构（lint、脚本、类型、校验器），文本只留给结构管不了的判断。
3. 多步编排、要派 subagent、有检查点回复 → playbook，不是技能。
4. 广泛适用的价值判断 → principle，不是技能。
5. 一次性任务、只服务单个会话 → 直接写在任务里。

技能的地盘：一个会重复出现、且只在特定情境需要、文本是最便宜载体的纪律。

## 定边界

- 一个技能一件事。两件事就两个技能，互相引用。
- description 是路由面：模型只看它决定加载。说清做什么、何时用（pi 标准），再补一行何时不用（本门槛加码）。
- 触发条件写情境可观察的特征（「多步功能」「引证答案」），不写抽象品质（「复杂任务」）。
- 窄触发：宁可漏掉边缘场景，不可宽到与邻居双触发。有邻居时写一行分工（谁主导、谁升级、谁让位）。
- name 用小写字母数字连字符，上限 64 字符；description 上限 1024 字符，超限或非法会被静默跳过。

## 定形状：纪律，不是流程手册

技能装载后与任何正在跑的流程（用户的、playbook 的）叠加，所以写完备性门槛，不写执行脚本。清单项按依赖顺序排列，允许来回，不允许漏项。

每个节必须改变一个决策，否则删。常用骨架，按需取用：

- 目标：产出什么，一句话。附一句「什么情况不该存在」。
- 何时用 / 不用：与 description 同口径，正文可展开。
- 原则：价值判断，为什么这么设计。
- 纪律或门槛：可验证的完备性清单，用「动手前必须能回答」「心智模型必须包含」这类句式。
- 交付物：默认产出长什么样。
- 护栏：明确不做的事。
- 表达：一行指向项目写作规范，只补技能特有的一条。

## 质量门槛

交付前逐条过：

- frontmatter 有 name 与 description，格式合法。
- 只读 description 就能决定「用还是不用」。
- 引用的文件存在，交叉链接可解析。
- 不复述每轮在场的系统提示或规则内容；确需强化的，写成差异而非重复。
- 结构性断言（frontmatter、链接、触发词）配测试或脚本；主观判断明说它是判断。
- 全文没有只有作者能懂的词；术语首现即释。

## 验证与进化

- 上线判据是真任务：拿一个该触发的场景跑一遍，行为可观察地变了才算数；再拿一个不该触发的场景跑一遍，没加载才算数。
- 上线后靠复盘回填：会话复盘（reflect 类机制）把漂移与缺失路由回具体修改。
- 删除判据：想不起来它最后一次改变决策是什么时候，就该删。

## 与邻居的分工

- poteto 的 authoring-a-skill playbook：poteto 主导时它的检查清单与 PR 流程叠在本技能之后跑，不冲突。
- pi 文档 skills.md：格式与加载标准的权威出处，本技能不复述标准细节。
- unslop / technical-writing：正文文风交给它们，本技能只管结构与边界。
- encode-lessons-in-structure 原则：同一主张的两个落点，先查结构再写文本。
