# 读懂这个代码库

## 目标

对陌生或半熟的代码建立**够用的最小心智模型**。

不是读完讲全。是理解相关系统到这个程度：能导航、能推理、能安全动手、知道下一步该查哪。

## 原则

- 理解范围跟着当前目标走。
- 大仓库里与本范围无关的部分当黑盒，除非它影响当前范围。
- 先懂行为与架构，再钻底层实现。
- 端到端流程优先，逐文件讲解靠后。
- 注意力按业务重要性与风险分配。
- 分清代码证明了的和只是推断出来的。

## 流程

### 1. 定范围

先定要理解什么：

- 整个系统
- 业务域
- 某功能
- 模块或服务
- 运行时流程
- 某个 bug
- 计划中的改动

有了范围，就不讲整个仓库。只有为理解上游触发、下游影响、共享数据、关键约束或外部依赖时才越界。

### 2. 画地图

给相关区域建一张紧凑地图：

- 入口
- 重要组件
- 业务逻辑
- 持久化
- 基础设施
- 外部集成

按职责讲清每个重要组件——不是只报文件名。关系难懂时配一张小图。

### 3. 走流程

顺着当前目标最重要的端到端流程走。每条流程讲清：

- 什么触发它
- 从哪进入
- 哪些组件参与
- 关键决策发生在哪
- 什么数据变了
- 产生哪些副作用
- 产出什么结果

有用时引用具体的文件、类、函数、测试。

### 4. 划边界

识别：

- 谁拥有重要行为与数据
- 关键依赖
- 公共接口或契约
- 副作用边界
- 可疑的耦合与归属不清

不发明仓库里实际不存在的更干净架构。

### 5. 找规则

识别对当前范围要紧的约束：

- 业务规则
- 重要不变量
- 一致性假设
- 权限或归属规则
- 其他必须恒真的条件

结论标注三档：

- **实测**——有代码、配置或测试直接支撑。
- **推断**——证据指向的大概率意图。
- **未知**——无法可靠确立。

### 6. 风险与下一钻

只点出值得更深理解的区域：

- 核心业务行为
- 重要副作用
- 数据一致性
- 并发或事务
- 安全边界
- 复杂耦合
- 测试薄弱或缺失

推荐少量有用的深钻点，然后停。

## 改动模式

目标是一次具体改动时，分析围绕这条线收敛：

**当前行为 → 改动面 → 依赖 → 不变量 → 风险 → 验证**

只理解到能安全改动的程度。实现后，把实际改动与预期改动面对账，报告有意义的意外影响。

## 默认产出

第一轮保持紧凑：

1. 范围
2. 系统一段话
3. 相关地图
4. 关键流程
5. 重要规则与不变量
6. 风险区
7. 下一步看哪

不自动滑进穷尽式实现细节。解释用项目既定领域术语（`.hapilon/CONTEXT.md` 有词汇表就用），说团队的语言。

## 护栏

- 不倒仓库目录树。
- 不讲无关模块。
- 不拿文件清单冒充理解。
- 不用自信的语气藏不确定性。
- 不展开对当前目标无益的深层实现细节。
- 人有足够上下文做下一个决策了，就停。

## 表达

平实、具体。

- 项目行话翻成大白话，同时保留真实标识符供搜索。
- 生僻缩写首现即释。
- 具体执行流程优先于抽象描述。
- 标识符永远连着它的含义与职责。
- 实测事实、推断、未知分开说。
- 不造词、不喊口号、不注水、不反复总结、不加没用的小标题。
- 从简单起，确有必要再加细节。
