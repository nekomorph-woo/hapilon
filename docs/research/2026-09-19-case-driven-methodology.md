# Case 驱动开发方法论 · 为什么与设计决策链

日期：2026-09-19 · 来源：`golden-case` 技能落地的完整过程（需求 → 规范 → 脚本 → 技能 → 复盘）
状态：方法已落地为 hapilon 内置技能；本笔记沉淀「为什么」与当日真实教训，不重复技能文档的操作步骤。

## 1. 问题：AI 写代码，凭什么说「完成」

传统验收的完成判据是「代码写完 + 测试绿」。这套判据在 AI 协作下有三处漏：

1. **绿可以是买来的。** 测试红了，AI 最省力的修法是把期望值改成实际值——测试转绿，bug 留下。这不是假设：本方法的演示 fixture 里就有一个这样的作弊件（`CASE-003` 含税总价实现错成 76.8，期望被从冻结值 74.8 偷改成 76.8）。
2. **测试可以只在测 mock。** 把余额、库存这类**观察面本身**也 mock 掉，测试永远绿，因为它比的是 mock 与 mock。
3. **判卷器自己可能失信。** 规格写了 `>=`，判卷器按 `==` 判——视图里写着「≥」，判定按「=」，结果不可信而无人察觉。当日实测正是这个 bug（详见 §5）。

于是完成判据换个锚点：**不以「代码写完」为准，以「case 被满足、验证点通过、实际结果符合预期」为准**。先定义什么是正确，再让 AI 写测试与实现。

## 2. 方法：case 的四段结构 + 三问 + 五类观察点

### 2.1 四段结构（SPEC / VERIFY / EXECUTION / RESULT）

一个 case 不是一段测试代码，而是四段各有业主的信息：

| 段 | 内容 | 回答的问题 | 业主 |
|---|---|---|---|
| **SPEC** | Given / When / Then + Invariant（场景、动作、结果白话） | 这个 case 想证明什么？ | 用户 |
| **VERIFY** | 结构化 Verification Point（source / operator / expected / actual） | 什么结果才算正确？系统具体如何验证它？ | 用户定期望，AI 提候选 |
| **EXECUTION** | Test + Dependency（framework / file / mode: MOCK·FAKE·LOCAL·REAL） | 用什么跑、在哪个世界跑？ | AI |
| **RESULT** | Run + 逐 VP 的 expected/actual/status + failure_stage | 现在过没过？没过从哪儿开始错？ | 机器 |

追踪链：Requirement → Case → Verification Point → Test → Test Run → Actual Result。
**Case 的 PASS/FAIL 由 VP 聚合产生**，首失败 VP 是调试的主入口——这是「从哪儿开始错」的答案落点。

### 2.2 三问（判据的原子单位）

每个观察点必须能回答三问，否则它只是一句愿景：

1. **看什么**（name / target，白话标签）
2. **去哪看**（source：观察面里的哪个锚点）
3. **看到什么算对**（operator + expected：比较符与金标）

`Verification Point` 就是这三问的结构化，`operator` 是第三问的机器形态。三问答不全 = 起草不合格，标注出来让用户补，而不是 AI 猜。

### 2.3 五类观察点（覆盖面检查表）

返回与状态 / 副作用 / 检查点路径 / 不变量 / 边界与异常。

这五类是**方法论固有的分类，不是项目配置**：它是「覆盖够不够」的检查表。某个类目在本 case 集里是 0 条时，那不是及格，是**覆盖缺口**，要在视图的覆盖条上当场暴露。当日 demo 集里「边界与异常」为 0，就是被这个方法自己照出来的。

### 2.4 人的四个控制点（介入曲线）

需求方只做四件事，其余交给 AI：

1. Case 是否正确表达需求（起草与审阅）
2. Expected 是否正确（封金）
3. 验证点是否足以证明（覆盖审计）
4. 测试是否忠实实现 Case（而不是为通过改预期）

对应到工作流就是五个「停下找用户」的关口：**draft → view/review → freeze → adapter → report/audit**。每阶段末尾一个 Stop：只做这一阶段，不自作主张往下跑，更不自我批准金标。介入被刻意压在「判定标准」这一侧，实现侧 AI 全权——这是效率与信任的分界。

### 2.5 六个不变量（写成铁律）

1. 观察面之内永不 mock，观察面之外随便 mock
2. 适配器零期望字面量（断言值从 case 文件加载，锚点串是唯一允许的字面量）
3. 适配器不接管单元测试（L1 全 mock 逻辑验证是 AI 自己的地盘）
4. 冻结后 Expected 只有用户能改
5. 期望必须可判定（数字、布尔、短 ASCII 符号；「余额正确」是描述不是期望）
6. 金标出自人，绝不出自实现的快照

## 3. 机制：这些约束怎么被机器守住

### 3.1 金标出自人 ≠ golden-master

与传统 golden-master 测试的区别是宣言级的：golden-master 把实现当前的输出**回抄**成基准，于是基准随实现漂移，bug 被固化成「正确」。
本方法里 Expect 只能由人定义或确认；**从实现跑出来的输出永远不能反向变成金标**。运行值只进 `RESULT`，进不了 `SPEC/VERIFY`。

### 3.2 freeze：把「为转绿改期望」变成红灯

`frozen.md` 是用户确认过的金标快照。`freeze-check.mjs` 做快照与 case 集的 diff，红牌三类：

- `CHANGED` 期望值被改
- `KEY-REMOVED` 期望键被删
- `CASE-MISSING` 冻结的 case 从 case 集里消失（通常意味着期望被「改走后删掉」）

命中即 exit 1，可直接当 CI 门。冻结之后实现、重构、日志、测试随便改；要改期望，唯一途径是新 case 版本 + 用户重新确认。

### 3.3 mock 边界 = 观察面

「观察面之内永不 mock」不是洁癖，是这条边界的定义：mock 掉余额/库存/事件流，测试就退化成「mock 与 mock 比」。反过来，支付网关、MQ、LLM、时钟在观察面之外，随便 mock，且**在那个 case 的 `dependencies[].mode` 里写明白**（MOCK / FAKE / LOCAL / REAL），让「这个 case 在哪个世界跑」成为数据而不是口口相传。

### 3.4 A/B 适配器：把「谁坏了」也变成可判定的

同一个 case 可以挂两个适配器：A 用 mock 依赖，B 用真依赖。
**A 绿 B 红 = 业务正常、模型层异常**——失败被定位到层，而不是笼统一句「测试挂了」。真依赖那侧的配置只引用环境变量名，密钥本身永不进 case 数据。

### 3.5 首失败定位

`report.mjs` 把测试输出按锚点（`CASE-003:checkpoint_c_total`）聚合成 case 块，每个 case 的首个失败 VP 置顶。于是「哪儿开始错」不需要人去读测试代码：从首失败 VP 顺藤摸到 source，再摸到实现。

### 3.6 判卷内核：operator 真分发 + fail-closed

VP 的 `operator` 必须有对应语义，且**认不出的情况不许静默降级**：

- 六个承诺的比较符（`== != >= <= > <`）全部真生效，边界相等按数学语义
- 空 operator 按 `==`（v1 数据兼容）
- **未知符号 → FAIL + message 点名该符号**（不静默当 `==`）
- **非数值遇有序比较 → FAIL + message 说明无法比较**（`Number('') === 0`、`Number(null) === 0` 会把「没值」悄悄当成「零」，是同个 bug 的另一种形态，故显式解析）
- 描述性（不可判定）期望**不参与判定**，标 `bad` 并把 case 健康度置 `BROKEN`——拒判而非乱判

## 4. 落地：技能与脚本

`resources/skills/golden-case/`（零依赖 Node，无构建步骤）：

| 部件 | 职责 |
|---|---|
| `SKILL.md` | 五阶段工作流 + 六铁律 + 反模式，供 AI 按需加载 |
| `references/format.md` | case 文件 schema、受控词表、runs.json 形态、Java(JUnit 5)/pytest 适配器模板 |
| `scripts/yaml-lite.mjs` | case 用 YAML 子集解析 + `numEq` / `isUndecidable` / `isDecimal` |
| `scripts/cases-source.mjs` | `--cases` 来源解析（单文件 / 目录按文件名序合并 / 逗号列表，重复 id 后者覆盖） |
| `scripts/gen-view.mjs` | 静态审阅视图（manager / workbench / ledger / dossier / narrative / index 六 style） |
| `scripts/explorer.mjs` + `explorer-client.js` | 交互式审阅面：Card/List、筛选、Drawer、便签、History、Prompt Composer（数据与客户端代码内联的只读单文件） |
| `scripts/freeze-check.mjs` | 冻结快照守门 |
| `scripts/audit.mjs` | case ↔ 测试代码对账，三类异常：UNOWNED / ORPHAN / LITERAL |
| `scripts/report.mjs` | 测试输出 → 按 CASE 聚合，首失败 VP 置顶 |

产物定位：case、frozen、视图、`runs.json`、`runs-history/` 全在项目 `.hapilon/go-case/` 下（本地、不入仓）；唯一入仓的是项目真实测试目录里的适配器。

**实际形态**（demo 订单域，6 个 case，渲染 18 个 VP）：`CASE-001` 返回值+状态+不变量（含 `>=` 的机器形态 VP）、`CASE-002` 副作用恰好一次、`CASE-003` 三段检查点路径（含税价）、`CASE-004` 钱货两清（REGRESSION 型，带不变量）、`CASE-005` 支付重试幂等（不变量 case，PLANTED BUG B）、`CASE-006` 未实现功能的 `EXPECTED_RED`（与 `UNEXPECTED_FAILURE` 区分：前者是「功能没做」，后者是「环境炸了」，两者必须能分辨）。

判卷/审计脚本本身也受回归保护：`src/test/unit/golden-case-scripts.test.ts` 内联固定数据跑真 CLI，覆盖 operator 内核（含 fail-closed、v1 派生兼容）、freeze-check 红牌与全绿对照、audit 三类异常与零异常对照、yaml-lite 不可判定拒判，随 `npm run test:unit` 一起跑。

## 5. 今日三类真实教训

### 5.1 判卷器与规格不一致（operator 域）——已定位并修复

**症状**：`format.md` 承诺了比较符、视图渲染了「怎么判断」，但判定一律走 `numEq(expected, actual)`：写了 `>=` 的 VP 被按 `==` 判。

**根因**：判定内核把 `operator` 当了装饰，`buildRun` 里没有分发。

**修法**：判定收拢到一个 `judgeVp(operator, expected, actual)`，六个符号真分发，两条 fail-closed 路径各有可区分 message（§3.6）。客户端一行未改——它只聚合预计算结果，不做二次判定，所以判定语义只有一处。

**验证**：端到端跑真 `explorer.mjs` 再从事物 HTML 读回判定结果（内核未导出，且要保证的正是「写进 YAML 的 operator 一路走到视图里的 status/message」）。变异测试：把内核改回 `numEq` 后 4 例转红、v1 派生那例仍绿——证明断言盯住的是这个 bug，而 v1 行为确实没变，不是「碰巧也绿」。

**留下的教训**：修复时回归测试只写在档案目录，不在仓库、不进 `test:unit` 的收集范围——修好了但**没有人自动拦住它回来**。本次收尾已把它迁进仓库受测。判卷器是这套体系的信任核心，它的回归网不能建在仓库外。

### 5.2 推理模型空响应——根因未定位，防线不等于根因

**症状**：recap 调模型时拿到空正文，界面报「模型未返回有效内容」。

**过程（含一次自我更正）**：第一轮给出「思考与正文共享 max_tokens，小预算被思考吃光」的根因，据此加了推理分支参数与更大预算；随后用 wire 捕获 + 实调证伪了该假设（该家族在参数缺省时显式 `thinking:disabled`，旧参数下 5/5 非空、reasoning token 恒 0）。**原始空正文的成因至今未定位**，如实记为「疑为服务端偶发」。

**最终修法**：不再声称修根因，而是加防线——预算递增重试 `[256, 1024, 4096, 4096]`（小预算先走，全空才 warn + failure widget），并把「键名家族限定」这类硬事实写进注释。

**教训**：① 根因未定位就写未定位，不把防线包装成根因；② 更正要就地标注、保留原叙述，不静默重写历史。另有一条工程教训同样值得记：同期发现该测试文件里一个既有竞态，不修它「全绿」就是假绿——**绿本身也要被怀疑**。

### 5.3 Gate 误拦——误伤的代价，以及「摩擦不可观测」

**实测**：66 个 session、2630 次 bash 调用，挖出 108 条真实 BLOCK 留痕（4.11%）；逐条核对，**真危险命令 0 条**——全是 grep/find/sed/统计类只读命令。根因是旧分类器对**整条命令**做正则：任何 `$()`、反引号、引号内的危险词都直接 block。

**后续**：其中的 95.4%（103/108）已被 09-13 的分类器重构（只读跳过、去引号视图、逐简单命令判定）消化，剩余 6 条经核验是旧构建/旧进程，零新增。

**教训（对本方法更重要的那条）**：弹窗批准在会话留痕里**零记录**——能挖到的只有硬阻止，弹窗造成的停顿（worker pane 被弹窗卡死，golden-case 两次各卡 90 分钟）在日志里不可见。**观测面缺了「摩擦」这一格，于是最贵的代价不可度量。** 规则层的正确性只解决了一半问题；「谁来判定、判定失败时人怎么被叫醒」也是方法论的一部分——这与 case 体系里「拒判而非乱判、失败要指向人」是同一条原则的两处应用。

## 6. 已知边界与后续

**如实记录的边界（当前未做/未定位）**：

1. **operator 只在 `runs.json` 判定路径生效**：带内联 `latest_run` 的 case 直接信托运行文件里写好的 status，不走 operator 判定；要按 operator 判就得走 `--runs`。
2. **同一 case 内两个 VP 共用同一个 `source` 时结果会串**：结果按 `vp_id` 或 `source` 匹配，后者先命中即复用（写回归测试时实测：同一 source 上放一个 `>=` 与一个 `==` 的 VP，后者被前者的判定结果覆盖）。规避用法是同一 source 只挂一个 VP；根因未修，因为修它要动 runs.json 的取值键形态（一次计划中的格式变更）。
3. **`yaml-lite` 是子集**：不支持锚点、多文档、多行标量、值内 `#`；小数按文本保留（为了视图单位与 freeze 数值比较）。
4. **`audit` 的 LITERAL 探测是启发式**：小于 10 的整数不报（测试代码常见噪音），有漏报与误报的天花板，嫌疑值最终由人裁决；这一点脚本自己就标注了天花板与升级路径。
5. **v1 降级展示**：旧 case 没有 v2 字段时分组落「未分类」、观察点标签回落机器名——刻意不猜、不编造。
6. **推理模型空响应的根因未定位**（§5.2），现有的是防线而非修复。
7. **Gate 摩擦无留痕**（§5.3），「弹窗批准」不进日志，摩擦只能靠用户证词估算。

**有意不做**：不碰单元测试（L1 全 mock 逻辑验证是 AI 自己的地盘，不进本技能的覆盖指标）；不做 L1–L4 硬框架（分层是适配器策略，不是 harness 结构）；不改常驻系统提示（方法论按需加载）。

**下一步（有证据支持的方向）**：

- 把「同一 source 多 VP」的键形态一并改掉（边界 2 的根因），顺带让内联 `latest_run` 走同一套判分词（边界 1）。
- `gen-view` 的 business 分组仍与 explorer 的 `--business` 不对称（已知偏差，未做）。
- 真实项目首跑：本方法的证据目前主要来自 demo 域与技能自身的回归面，尚未在真实业务仓库上验证「介入曲线」的实际成本。

---

**一句话**：这套方法把「什么算对」从实现里剥离出来交给人，再用机器守住四条线——金标只出自人、冻结后只有人能改、观察面不被 mock、判卷器认不出的情况一律拒判。当日三类事故正好分别检验了其中三条：判卷器失信（`operator` 未分发）、根因诚实（未定位就说未定位）、以及观测面缺格（摩擦不可见）。
