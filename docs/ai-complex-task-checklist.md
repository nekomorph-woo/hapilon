# AI 复杂任务检查清单

> 适用：数据整理、报告、分析、方案、看板、研发审核、知识库、项目规划等“开始时说不清，最后要交付”的任务。
>
> 主流程：**0 Dump → 1 Explore → 2 Frame → 3 Define → 4 Design → 5 Prototype → 6 Inspect → 7 Scale → 8 Freeze**
>
> 相比之前的 8 步，新增 **Stage 0：Dump / 起手式**。原因是现实里最难的经常不是“不会执行流程”，而是“一开始脑子空，不知道第一句话怎么说”。

---

## 0. Dump｜先把脑子里的东西倒出来

### 只问这一句
**我现在到底有什么？哪怕很乱。**

可以直接给 AI：领导一句话、旧报告、Excel/HTML/Markdown、截图、仓库、数据源、抱怨、直觉，以及“我也不知道该做成什么”。

### 检查清单
- [ ] 已把主要材料交给 AI
- [ ] 大致说明最终给谁看
- [ ] 说明最困惑或最不满意的地方
- [ ] 允许自己说“不知道”
- [ ] 没有要求 AI 直接做最终成品

### 最低可用 Prompt
```text
我现在还没有完整方案，先不要直接做最终交付物。

这是我目前知道的材料、数据源、旧产物和一些零散想法：
[材料 / 文件]

请先做 Discovery：
1. 梳理已确定事实；
2. 区分事实、我的猜测、你的推测；
3. 找出关键未知项和矛盾；
4. 判断这个任务可能真正要解决的问题；
5. 暂时不要替我拍板最终方案。

如果信息不足，优先暴露“不知道什么”，不要为了完整而补全。
```

### Gate 0
- [ ] AI 没有直接跳成品
- [ ] 已出现“已知 / 未知 / 冲突”的地图
- [ ] 问题开始成形

---

## 1. Explore｜探索事实和材料

### 核心问题
**客观世界现在是什么样？**

### 检查清单
- [ ] 有哪些数据源
- [ ] 哪些是权威源
- [ ] 哪些是历史遗留
- [ ] 字段 / 文件 / 仓库分别代表什么
- [ ] 哪些数据冲突、重复、缺失
- [ ] 哪些实现细节不应直接进入最终表达
- [ ] 哪些术语看似相同，其实含义不同
- [ ] 哪些判断只是推断

### 最低可用 Prompt
```text
先只做事实梳理，不做最终方案。

请输出：
- 已确认事实
- 数据源及可信度
- 术语及含义
- 冲突 / 缺失
- 当前无法确认的事项

不要把建议混成事实；推断请明确标记。
```

### 推荐产物
`discovery-notes.md` / `source-map.md` / `fact-unknowns.md`

### Gate 1
- [ ] 事实与建议已经分开
- [ ] 知道哪些源最可信
- [ ] 主要口径冲突已暴露

---

## 2. Frame｜定义真正的问题

### 核心问题
**谁要用这个东西？他看完要做什么判断？**

### 检查清单
- [ ] 主要用户是谁
- [ ] 用户是什么角色
- [ ] 用户不是什么角色
- [ ] 用户最先想知道什么
- [ ] 用户看完要做什么判断 / 决策
- [ ] 什么信息是噪音
- [ ] 什么虽然存在但不该进入主链路
- [ ] 做错最可能怎样误导用户

### 最低可用 Prompt
```text
先不要讨论页面、代码或格式。

请帮我定义：
1. 主要用户是谁；
2. 用户最重要的 3～5 个判断是什么；
3. 用户不需要直接看到什么；
4. 做错最可能怎样误导用户；
5. 用一句话定义这个交付物是什么。

如果存在多个合理定位，列出候选，不要直接替我拍板。
```

### Gate 2
你至少能说出：

> 这是给 ___ 看，用来判断 ___ 的，不是用来 ___ 的。

---

## 3. Define｜钉死概念、口径和边界

### 核心问题
**我们嘴里说的这些词，到底是什么意思？**

永远分四类：

- **Fact**：客观事实
- **Decision**：已拍板规则
- **Unknown**：当前不能可靠判断
- **Proposal**：建议，还没成为规则

### 检查清单
- [ ] 核心指标有定义
- [ ] 分子 / 分母清楚
- [ ] 什么算完成
- [ ] 什么明确不算
- [ ] 哪些状态允许“不知道”
- [ ] 是否用了代理指标
- [ ] 代理有没有被包装成真实结果
- [ ] 是否有必要的“反定义”

### 最低可用 Prompt
```text
请把核心概念整理成 Definition Spec。

每个概念都写：
- 是什么
- 不是什么
- 数据从哪里来
- 当前能不能可靠计算 / 判断
- 如果不能，应该如何表达未知

同时维护：Fact / Decision / Unknown / Proposal。
不要为了让指标完整而补造公式或数据。
```

### 推荐产物
`definitions.md` / `metrics-spec.md` / `decision-log.md`

### Gate 3
- [ ] 同一个词只剩一种主要含义
- [ ] Unknown 被保留
- [ ] Proposal 没偷渡成 Decision
- [ ] 代理没有写成真实结果

---

## 4. Design｜先设计信息，不急着实现

### 核心问题
**用户应该按什么顺序看到什么？**

### 检查清单
- [ ] 第一眼看什么
- [ ] 第二眼看什么
- [ ] 主阅读链是什么
- [ ] 什么默认隐藏
- [ ] 什么只能下钻
- [ ] 空数据如何展示
- [ ] 异常状态如何展示
- [ ] 信息层级是否与业务层级一致
- [ ] 是否出现“实现结构绑架业务结构”

### 最低可用 Prompt
```text
现在进入信息架构阶段，但先不要写代码。

请根据：
- 用户是谁
- 他要做什么判断
- 已确认的定义与边界

设计：
1. 信息主链路；
2. 页面 / 报告层级；
3. 首屏 / 首段必须出现的内容；
4. 默认隐藏和下钻信息；
5. 空数据、缺口、待确认状态；
6. 交互或阅读顺序。

先给 wireframe / Markdown 结构，不实现。
```

### 推荐产物
`information-architecture.md` / `wireframe.md` / `design-spec.md`

### Gate 4
> 不看实现细节，我能不能顺着这个结构完成主要判断？

---

## 5. Prototype｜只做最小但最有代表性的原型

### 核心问题
**这套设计在极端情况下还成立吗？**

### “一肥一瘦”原则
一个选：数据最多 / 情况最复杂 / 信息密度最高。

另一个选：数据最少 / 缺口最大 / 异常最明显。

### 检查清单
- [ ] 最复杂案例不会撑爆结构
- [ ] 空数据不会被隐藏
- [ ] 少量证据不会被误判成“完成”
- [ ] 同一结构能兼容两极
- [ ] 没有大量样例特判

### 最低可用 Prompt
```text
不要全量实现。

请从当前数据中选择：
- 一个最复杂 / 数据最多的案例
- 一个最空 / 最异常的案例

只用这两个案例做 Prototype。
目标是验证信息架构、异常状态、缺口表达和默认信息密度。
```

### Gate 5
- [ ] 一肥一瘦都自然
- [ ] 缺口能被明确看到
- [ ] 没有为了某个样例破坏整体结构

---

## 6. Inspect｜从“会不会运行”升级成“会不会误导”

### 核心问题
**这个成品实际打开以后，会不会让我形成错误判断？**

### 技术检查
- [ ] 能打开
- [ ] 交互正常
- [ ] 数据正常
- [ ] 默认状态正常

### 语义检查
- [ ] 0 没有被隐藏
- [ ] Unknown 没被包装成结论
- [ ] 代理指标没写成真实结果
- [ ] 数量没被误读成质量
- [ ] 默认展开与文案一致
- [ ] 第一眼没看错重点
- [ ] 结论没有超过证据边界

### 最低可用 Prompt
```text
现在不要继续加功能。
请切换成 Reviewer。

实际打开 / 运行当前产物，从用户视角检查：
1. 第一眼会看到什么；
2. 哪些地方可能误导；
3. 哪些状态只在代码里正确、界面上却表达错误；
4. 默认展开、空数据、缺口、异常数据是否真实；
5. 哪些结论超出了证据。

输出 self-review，并修复明确问题。
```

### Gate 6
> 如果它错了，会怎么骗到我？

---

## 7. Scale｜通过原型后再扩全量

### 核心问题
**是在复制已验证模式，还是重新发明系统？**

### 检查清单
- [ ] 只扩数据，不乱改核心结构
- [ ] 新情况先标 Unknown / Proposal
- [ ] 不因“收全数据”偷偷改口径
- [ ] 新异常状态有显式说明
- [ ] 一肥一瘦继续做回归样例

### 最低可用 Prompt
```text
Prototype 已通过。
现在扩展到全量数据，但遵守：
- 不修改已确认的信息架构；
- 不新增正式业务层级；
- 无法归类时标 Unknown；
- 需要改规则时先输出 Proposal；
- 保留一肥一瘦两个样例做回归检查。
```

### Gate 7
- [ ] 全量扩展没有冲掉原型阶段的正确原则
- [ ] 没有为了方便实现而重定义业务

---

## 8. Freeze｜把最终经验写回系统

### 核心问题
**下次重新开会话，还需要从头解释吗？**

### 必须沉淀
- [ ] 最终 Spec
- [ ] Decision Log
- [ ] 数据源说明
- [ ] Unknown / Backlog
- [ ] 验收规则
- [ ] 被否决方案
- [ ] 下一步计划
- [ ] 新 Start Prompt

### 最低可用 Prompt
```text
任务进入收口阶段。
请不要再设计新方案，而是做知识固化：
1. 把最终确认口径写回 Spec；
2. 更新 Decision Log；
3. 记录仍然存在的 Unknown；
4. 记录被否决方案及原因；
5. 整理下次重新启动最少需要读取的文件；
6. 给出新的 Start Prompt，确保换模型 / 换会话也能继续。
```

### Gate 8
> 新模型只读这些文件，能否快速恢复上下文并继续工作？

# 脑子空白时，只记这 6 句话

```text
1. 我现在还不知道最终该做成什么，先帮我梳理现状，不要直接做成品。

2. 请区分：事实、我的猜测、你的推测、待确认项。

3. 谁会看这个东西？他看完真正要做什么判断？

4. 先把核心概念定义清楚，尤其告诉我“什么不算”。

5. 先做信息架构和两个极端样例，不要全量实现。

6. 现在切换成 Reviewer：这个东西最可能怎样误导我？
```

# 你的角色：Gate Keeper，而不是超级老师

你负责：

- 目标
- 边界
- 拍板
- Gate
- 验收

AI 负责：

- 搜索
- 整理
- 提炼
- 候选方案
- 实现
- 自检

你的核心问题始终是：

> **现在可以进入下一步了吗？**

这就是“智能中枢”。
